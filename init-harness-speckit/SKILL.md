# init-harness-speckit

Adds the **harness as a governance layer over an existing spec-kit repo**.
Spec-kit is the artifact pipeline (`spec.md`, `/speckit-*`); the harness adds
what spec-kit lacks — a `covers:` scope bound, a `verify:` proof command, and a
human `draft → active` plan gate. It never replaces spec-kit and never
hand-edits spec-kit's generated files.

This is the spec-kit-aware sibling of `init-harness`. Where `init-harness` puts
plans in `docs/exec-plans/`, this skill makes `specs/<feature>/plan.md` (the
spec-kit plan artifact) the single authorized plan. The reference
implementation is `be-paris-backend-cl-ms-search`; this skill replicates it.

## Precondition — spec-kit must already be installed

The target repo MUST already have spec-kit: `.specify/templates/plan-template.md`
and `.specify/memory/constitution.md` must exist. If they do not, **halt** and
tell the user to run spec-kit init first (`specify init`), then re-run this
skill. This skill layers on top; it does not install spec-kit.

## The integration model

Per [ADR speckit-harness-integration], the constitution is supreme and the
harness sits *beneath* it as the process layer. The harness edits exactly **one**
spec-kit file and adds everything else alongside:

| Spec-kit file (MODIFIED, surgical) | Change |
|---|---|
| `.specify/templates/plan-template.md` | prepend harness frontmatter (`ticket/status/covers/verify/analyzed`); replace the Constitution Check placeholder with a gate that points at `constitution.md` plus the two harness controls (`covers:`, `verify:`) |

Everything else is **added, not merged into spec-kit**: `.specify/extensions.yml`
(hooks at spec-kit's native extension points), the four `harness-*` hook skills,
`scripts/harness/`, `docs/`, and the repo-root anchors.

**`constitution.md` is never touched.** It is the project's highest-authority
document and is owned by the team via `/speckit-constitution` (spec-kit's
official flow). The harness governs *process* (`covers:`/`verify:`/gate/loop),
not the constitution's *principles*; `AGENTS.md` defers to the constitution.

**Also never touched:** `.specify/scripts/bash/*`, the neutral templates
(`spec/tasks/checklist/constitution-template.md`), and the generated
`.claude/skills/speckit-*` / `.agents/skills/speckit-*` skills. Those are
regenerated by the `specify` CLI, never hand-edited.

## Versioning

Versioned with **semver**, in `VERSION` (single line). Each release records its
changes in `versions/<X.Y.Z>.md` — self-contained, with **What changed** +
**How to apply** (idempotent, check-then-act). A repo learns what changed by
reading **only the version files newer than its own `.harness-version`**.

Bump levels: **patch** (fix to an existing file, silent re-run), **minor**
(additive file/section, idempotent re-run), **major** (moved/renamed/removed
file or changed contract, re-run shows a diff and requires confirmation).

Scaffolded repos record the applied version in `.harness-version` at their root.

## How to update this skill

    ./bump-version.sh {major|minor|patch}

It computes the next semver, scaffolds `versions/<next>.md`, and updates
`VERSION`. Fill the two sections, edit the asset(s), then stage **asset +
VERSION + versions/<next>.md** in one commit. The pre-commit gate
(`.githooks/pre-commit`) refuses any commit touching `assets/` or `SKILL.md`
unless `VERSION` was bumped and a filled-in `versions/<VERSION>.md` is staged.
Activate it: `git config core.hooksPath init-harness-speckit/.githooks`. Bypass:
`INIT_HARNESS_SPECKIT_BYPASS="<reason>" git commit ...`.

## Modes of operation

Read the target repo's `.harness-version` and compare to this skill's `VERSION`:

| Target state | Mode | Action |
|---|---|---|
| No `.harness-version`, no harness files | **Scaffold** | Steps 0–12; write `.harness-version` = `VERSION` |
| No `.harness-version`, harness files present | **Adopt + upgrade** | Assume baseline `1.0.0`; fill missing files; then run the upgrade delta |
| `.harness-version` < `VERSION` | **Upgrade** | Skip scaffold; apply the version delta |
| `.harness-version` = `VERSION` | **Up-to-date** | No-op; report "harness is current at `<VERSION>`" |
| `.harness-version` > `VERSION` | **Skill behind** | Report; do nothing |

Determine mode before writing anything. All copies substitute `{{REPO_NAME}}`
(git dir basename or remote name) and `{{DATE}}` (today, ISO) in written files.

## Scaffold steps

### Step 0 — Preconditions and mode

Confirm a git repo. Confirm spec-kit is present (see Precondition); halt if not.
Resolve `{{REPO_NAME}}` and `{{DATE}}`. Determine the mode from `.harness-version`.

### Step 1 — Inspect what exists

List every file the skill would write or modify (Steps 2–11). Flag real
conflicts (an existing `AGENTS.md`, an existing `.specify/extensions.yml`, an
existing `github` entry in `.mcp.json`, an already-configured `core.hooksPath`
or hook-manager config, or `.pre-commit-config.yaml`). On a conflict, ask skip
/ overwrite / abort. A fresh spec-kit repo with no harness proceeds without
prompting. `constitution.md` is not in this list — the harness never modifies
it (Step 4).

### Step 2 — `.gitignore`

Append only what's missing to the repo-root `.gitignore`:

    __pycache__/
    **/__pycache__/
    *.py[cod]
    .claude/settings.local.json
    specs/**/.loop-state.json

### Step 3 — The one spec-kit edit: `plan-template.md` (surgical)

Edit `.specify/templates/plan-template.md` in place (do not overwrite the whole
file — spec-kit versions differ):

1. **Frontmatter.** If the file does not already begin with a `---` frontmatter
   block containing `covers:`, prepend the contents of
   `assets/plan-template-frontmatter.md` to the top of the file. Idempotent:
   skip if a leading frontmatter with `covers:` is already present.
2. **Constitution Check.** Replace the single placeholder line
   `[Gates determined based on constitution file]` with the contents of
   `assets/plan-template-constitution-check.md` — a gate that points at
   `.specify/memory/constitution.md` for principles and adds the two harness
   controls (`covers:`, `verify:`). It does **not** hardcode domain principles;
   those live in the repo's constitution.
   - If the placeholder is absent but the harness gate
     (`Constitution compliance:`) is already present → skip.
   - If neither is present (the section was customized) → **flag for manual
     review**; do not guess where the gate goes.

### Step 4 — `constitution.md` is left to the team (not modified)

**The harness does not author, overwrite, back up, or delete
`.specify/memory/constitution.md`.** It is the project's highest-authority
document, owned by the team via `/speckit-constitution` (spec-kit's official
flow). The harness is the process layer beneath it.

- Filled → leave exactly as-is.
- Still the unfilled template (`[PROJECT_NAME]` / `[PRINCIPLE_1_NAME]`) → leave
  as-is and flag: "constitution.md is the unfilled spec-kit template — fill it
  via `/speckit-constitution`; it is the supreme document and the plan
  Constitution Check gate reads from it."

`AGENTS.md` (Step 9) is written to defer to the constitution as the highest
authority.

### Step 5 — `.specify/extensions.yml` (hooks)

- Absent → copy `assets/extensions.yml`.
- Present → **do not clobber**. Show the five harness hooks (`before_plan`,
  `after_tasks`, `before_implement`, `after_tasks`→analyze, `after_converge`)
  and instruct a manual merge into the existing `hooks:` map. Flag.

### Step 5b — GitHub MCP server (spec-kit prerequisite)

Per [ADR speckit-harness-integration], the harness is **spec-kit-first**: where
spec-kit already has a native command, the harness provisions what that
command needs instead of shipping a parallel implementation.
`/speckit-taskstoissues` (generated by spec-kit, converts `tasks.md` into
GitHub issues) is written against the GitHub MCP server's `list_issues` /
`create_issue` tools — it does not fall back to `gh`. Without that server
configured, the command is present but non-functional.

- If no GitHub MCP server is already configured (no `github` entry in
  `.mcp.json`, no equivalent in another agent's MCP config) → write
  `.mcp.json` at the repo root pointing at the official GitHub MCP server run
  locally via Docker, with the token passed by reference to an environment
  variable — never written into the file itself:

  ```json
  {
    "mcpServers": {
      "github": {
        "command": "docker",
        "args": ["run", "-i", "--rm", "-e", "GITHUB_PERSONAL_ACCESS_TOKEN", "ghcr.io/github/github-mcp-server"],
        "env": { "GITHUB_PERSONAL_ACCESS_TOKEN": "${GITHUB_PERSONAL_ACCESS_TOKEN}" }
      }
    }
  }
  ```

  (Confirm the image ref and args against current GitHub MCP server docs at
  apply time — this is third-party surface the harness doesn't own.)

- `.mcp.json` already has a `github` entry → **do not clobber**. Flag for
  manual review.
- `docker` not on `PATH` → do not write `.mcp.json`. Flag in
  `docs/HARNESS-TODO.md`: install Docker, then re-run this step.
- Regardless of outcome, write to `docs/HARNESS-TODO.md`:
  1. Create a personal access token (scope `repo`) and authorize it for SSO
     against the org if required; export it as `GITHUB_PERSONAL_ACCESS_TOKEN`
     in your shell profile. The harness never writes the token itself — it is
     per-developer secret material, not repo state.
  2. Codex reads MCP servers from `~/.codex/config.toml`, a user-global file
     outside the repo — the harness does not write it. Add the equivalent
     `[mcp_servers.github]` entry there by hand; the snippet is in
     `docs/processes/dev-setup.md` § GitHub MCP server.

### Step 6 — Harness hook skills (canonical `.agents/` + symlink to `.claude/`)

The four `harness-*` skills live once under `.agents/skills/` and are symlinked
into the agent skill dirs — matching the reference repo and this repo's own
convention.

1. Create `.agents/skills/` if absent.
2. For each of `harness-gate`, `harness-verify`, `harness-loop`,
   `harness-implement-lite`: copy `assets/skills/<name>/SKILL.md` →
   `.agents/skills/<name>/SKILL.md` (skip if present).
3. Symlink into `.claude/skills/` (create it if the repo lacks it, though a
   spec-kit repo has it): `.claude/skills/<name> -> ../../.agents/skills/<name>`.
   If the repo has other agent skill dirs, symlink there too. On a filesystem
   where symlink fails, copy and flag "keep the two copies in sync manually".

### Step 7 — `scripts/harness/`

Copy and `chmod +x`:

- `assets/scripts/speckit_gate.py` — the gate/verify/loop engine the hook
  skills call (required).
- `assets/scripts/check_plan_coverage.py` — the one mechanical sensor (required).
- `assets/scripts/wt_fanout.sh` — optional loop helper referenced by
  `speckit-loop.md`; copy it too.

Converting `tasks.md` into GitHub issues is spec-kit's own job
(`/speckit-taskstoissues`, generated under `.claude/skills/speckit-taskstoissues/`
or `.agents/`), not the harness's — see Step 5b for what it needs to run.

Verify, and report PASS/FAIL:

    python3 scripts/harness/check_plan_coverage.py --selftest
    python3 scripts/harness/speckit_gate.py selftest

### Step 8 — `docs/` governance layer

Create `docs/decisions/` and `docs/processes/`. Copy (substituting
`{{REPO_NAME}}`, `{{DATE}}`):

| Asset | Destination |
|---|---|
| `assets/PLANS.md` | `docs/PLANS.md` |
| `assets/docs-README.md` | `docs/README.md` |
| `assets/harness.md` | `docs/processes/harness.md` |
| `assets/speckit-loop.md` | `docs/processes/speckit-loop.md` |
| `assets/dev-setup.md` | `docs/processes/dev-setup.md` (skeleton — flag needs-filling) |
| `assets/tech-debt-tracker.md` | `docs/tech-debt-tracker.md` |
| `assets/HARNESS-TODO.md` | `docs/HARNESS-TODO.md` (non-blocking checklist of every skeleton to fill) |

ADRs — for each, if absent copy; if present with a matching `id:` skip; if
present with a different `id:` halt with a conflict report:

| Slug | Asset |
|---|---|
| `harness-design` | `assets/harness-design.md` (leave `{{PROJECT_CONTEXT}}` if unknown; flag) |

### Step 9 — Repo-root anchors

- Copy `assets/AGENTS.md` → `AGENTS.md`.
- Create `CLAUDE.md` as a symlink to `AGENTS.md` (`ln -s AGENTS.md CLAUDE.md`).
  If a real `CLAUDE.md` already exists, do not clobber — flag it. If `ln` fails,
  copy and flag "keep in sync manually".
- Copy `assets/ARCHITECTURE.md` → `ARCHITECTURE.md` (skeleton — flag needs-filling).
- Copy `assets/SECURITY.md` → `SECURITY.md` (skeleton — flag needs-filling).

### Step 10 — Pre-commit wiring

The plan-coverage sensor is the harness's one mechanical control. Whether it
actually runs on every commit is a **convention, not a guarantee** — different
repos already have different hook stacks, and the harness never seizes
`core.hooksPath` away from a manager the repo already uses. What Step 10
guarantees instead: it either wires the sensor in cleanly, or it says exactly
what's missing in `docs/HARNESS-TODO.md` — it never claims wiring it didn't
verify. `check_plan_coverage.py --doctor` (Step 7) is the command that proves
which case actually happened, now and later.

**1. Detect the existing hook mechanism**, in this order:

- A YAML/JSON hook manager config at the repo root: `lefthook.yml` /
  `.lefthook.yml` / `.config/lefthook.yml` (lefthook), `.pre-commit-config.yaml`
  (pre-commit framework), or a `"simple-git-hooks"` key in `package.json` /
  a `simple-git-hooks.json` file (simple-git-hooks).
- Otherwise, resolve the effective hook file: `git config --get
  core.hooksPath` (if set, `<that dir>/pre-commit`) else `.git/hooks/pre-commit`.
  If that path exists (or the dir is a recognizable shell-hook manager like
  `.husky/`), it's a **shell hook**.
- Otherwise, no manager is present.

**2a. YAML/JSON manager found → never auto-edit it.** Merging into a
teammate's `lefthook.yml`, `.pre-commit-config.yaml`, or `package.json` risks
breaking every developer's commit pipeline if the merge is wrong, and the
skill cannot run the result to check. Instead, write a **blocking item** to
`docs/HARNESS-TODO.md` with the exact snippet to add by hand:

    python3 "$(git rev-parse --show-toplevel)/scripts/harness/check_plan_coverage.py"

**2b. Shell hook found (husky, vanilla `.githooks/`, plain `.git/hooks/`,
or any other manager whose hook file is a shell script) → extend it,
never replace it.** The manager keeps precedence over `core.hooksPath`; the
harness only appends to the hook file it already owns. Append, between
idempotent markers (create the file with a `#!/bin/sh` shebang first if the
manager hasn't written one yet):

    # >>> harness plan-coverage >>>
    python3 "$(git rev-parse --show-toplevel)/scripts/harness/check_plan_coverage.py"
    # <<< harness plan-coverage <<<

Check-then-act: if the markers are already present, skip. Never touch
`core.hooksPath` in this branch — the manager already owns it.

**2c. No manager at all** (no YAML/JSON config, no resolvable hook file,
`core.hooksPath` unset): copy `assets/pre-commit` → `.githooks/pre-commit`,
`chmod +x`, run `git config core.hooksPath .githooks`. This is the only
branch where the harness sets `core.hooksPath` itself, and only because
nothing else claims it. (`.git/hooks/` is never used as the harness's own
target even here — it isn't versioned, so it wouldn't survive a clone and
wouldn't show up in the PR that installs the harness.)

**3. Verify**, regardless of branch: run
`python3 scripts/harness/check_plan_coverage.py --doctor` and record its
verdict (`WIRED` / `UNWIRED`) for Step 12's report. On `UNWIRED`, Step 12's
manual-merge list carries the item forward — this is what keeps the doctor
verdict from silently rotting the way an unread TODO item does.

### Step 11 — `.harness-version`

Write this skill's `VERSION` value as a single line to `.harness-version`.

### Step 12 — Report

List **Created**, **Modified** (`plan-template.md` only), **Skipped (already
existed)**, and **Manual merge needed** (`extensions.yml`, a YAML/JSON hook
manager from Step 10, an existing `.mcp.json` `github` entry from Step 5b — if
flagged). For the skeletons that need repo-specific content, point at
`docs/HARNESS-TODO.md` — the non-blocking checklist the skill wrote
(`ARCHITECTURE.md`, `SECURITY.md`, `dev-setup.md`, `harness-design`
`{{PROJECT_CONTEXT}}`, GitHub MCP token/SSO/Codex config, and the constitution
via `/speckit-constitution`) — rather than re-listing them. State the
`.harness-version` written and whether the two selftests passed.

**State the pre-commit wiring verdict as measured, not assumed**: run
`python3 scripts/harness/check_plan_coverage.py --doctor` and report its actual
`WIRED` / `UNWIRED` output — never state that pre-commit is wired without
having just run this. On `UNWIRED`, surface the doctor's fix instructions
under Manual merge needed, exactly as printed, rather than paraphrasing them.
Also remind the user that since spec-kit's plan template now emits harness
frontmatter, the next `/speckit-plan` produces a harness-shaped plan.

## Upgrade delta procedure

Runs in place of the scaffold when `.harness-version` < `VERSION`.

1. Read the target's `.harness-version` (the marker).
2. **List** `versions/*.md` filenames — do not read contents yet.
3. Parse each as semver; select those **strictly greater** than the marker;
   sort ascending.
4. **Read only those files** — history below the marker is never read.
5. Apply each, oldest → newest: print the heading and **What changed**; execute
   the **How to apply** steps (idempotent check-then-act); for a **major**
   version show a diff and require explicit `y/n`; after each version verify,
   advance `.harness-version` to that version (persisted immediately).
6. If a target is locally modified such that the insertion point is ambiguous,
   **stop**, report the conflict, and leave the marker at the last clean version.
7. Report: which versions applied, which conflicted, the new marker.

## Notes on scope

- **Spec-kit is never replaced or regenerated.** Only `plan-template.md` is
  edited; its scripts, generated skills, and `constitution.md` are untouched.
- **The constitution is supreme and team-owned.** The harness governs process
  (`covers:`/`verify:`/gate/loop), never the constitution's principles;
  `AGENTS.md` defers to it.
- **Two mechanical sensors ship** — `check_plan_coverage.py` (pre-commit, the
  hard control) and `speckit_gate.py` (the gate/verify/loop engine the soft
  hooks call). Everything else is guide plus git pre-commit.
- **No agent-vendor coupling at the governance layer.** `AGENTS.md` is the
  cross-agent surface; the `harness-*` skills are thin adapters over
  `speckit_gate.py`.
- **Independent review is manual**, never gated.
