# 2.0.0 — Sensor wiring is honest, spec-kit-first for GitHub issues

## What changed

Fixes three bugs found in a PR review of 1.0.0 (two of them confirmed live in
every repo that installed 1.0.0 so far) and reframes one principle. `git mv`
no longer escapes `covers:` — `check_plan_coverage.py` now runs with
`--no-renames` and requires both endpoints of a rename to be covered, and its
own pre-commit gate got the same fix so a renamed asset can't skip the
version-sync check either. `speckit_gate.py`'s feature resolution now follows
spec-kit's own precedence (`SPECIFY_FEATURE_DIRECTORY` env var →
`.specify/feature.json` → single active plan) instead of letting
`feature.json` alone decide, and `gate` independently rejects more than one
active plan even when `feature.json` resolves cleanly — so it can no longer
approve a state the pre-commit sensor is about to reject. Both scripts gained
a way to answer "is the sensor actually wired?" as a measured fact instead of
an assumption: `check_plan_coverage.py --doctor` resolves the effective hook
file and reports `WIRED` / `UNWIRED`; `gate` and `gate-lite` call it and print
a non-blocking warning; Step 12's install report states the doctor's verdict
instead of asserting success. Step 10 (pre-commit wiring) is rewritten around
this: it detects an existing hook manager (husky, lefthook, the `pre-commit`
framework, plain `.githooks/`) and extends it in place for shell-based
managers (idempotent, marker-delimited append) rather than seizing
`core.hooksPath`, and defers YAML/JSON managers to a `docs/HARNESS-TODO.md`
item instead of risking a bad structural merge. Doc claims of unconditional
enforcement (`AGENTS.md`, `dev-setup.md`, `harness.md`, `harness-design.md`)
are softened to point at `--doctor` instead of asserting it. Separately,
`tasks_to_issues.sh` (a `gh`-based, harness-authored duplicate of spec-kit's
own `/speckit-taskstoissues`) is retired in favor of provisioning what the
native command actually needs: a new Step 5b writes `.mcp.json` for a local,
Docker-run GitHub MCP server (PAT passed by environment reference, never
written to the file) when no GitHub MCP server is already configured. Both
ADRs (`harness-design.md` § Sensor attachment, `speckit-harness-integration.md`
§ Spec-kit-first) are amended to record the reasoning behind both changes.

## How to apply

1. **Scripts are generated, not team-edited — overwrite in place.** Copy the
   new `assets/scripts/check_plan_coverage.py` and
   `assets/scripts/speckit_gate.py` over the existing
   `scripts/harness/{check_plan_coverage.py,speckit_gate.py}`, `chmod +x`.
   Re-run both selftests; report PASS/FAIL.
2. **Remove the retired script**, if present:
   `rm -f scripts/harness/tasks_to_issues.sh`. If `docs/processes/speckit-loop.md`
   still has the old "Issues" section referencing it (check for the literal
   string `tasks_to_issues.sh`), replace that section with the new one from
   `assets/speckit-loop.md`.
3. **Re-run Step 10's detection** against the repo's current hook setup and
   compare to what's actually wired today (`python3
   scripts/harness/check_plan_coverage.py --doctor`). If `UNWIRED`, apply
   Step 10's injection logic now; if already `WIRED` under the old
   `.githooks/` convention, leave it — this step is idempotent, not a forced
   migration off of a working setup.
4. **Provision the GitHub MCP server** per new Step 5b: if no `github` entry
   exists in `.mcp.json` and `docker` is on `PATH`, write it; otherwise add
   the corresponding item to `docs/HARNESS-TODO.md`. Skip entirely if a
   `github` MCP server is already configured some other way — flag, don't
   clobber.
5. **BREAKING — confirm before applying.** The following files may have been
   hand-edited by the team since scaffold, so show a diff against
   `assets/{AGENTS.md,dev-setup.md,harness.md,harness-design.md,
   speckit-harness-integration.md,HARNESS-TODO.md}` and require explicit
   `y/n` per file before overwriting: the enforcement-claim wording in
   `AGENTS.md` (§ Gates), `dev-setup.md` (§ Plan-coverage check, § Adding
   stack lanes, new § GitHub MCP server), `harness.md` (§ hooks are soft
   controls), and both ADR amendments (`harness-design.md` § Sensor
   attachment, `speckit-harness-integration.md` § Feature resolution
   precedence and § Spec-kit-first). `HARNESS-TODO.md` gains the four new
   conditional checklist items (append, don't replace, if the file has
   team-added content below the scaffolded checklist).
6. Advance `.harness-version` to `2.0.0` only after steps 1–5 complete without
   an unresolved conflict.
